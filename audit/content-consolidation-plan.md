# コンテンツ統合・独自価値強化 設計案（アルゴリズム降格からの回復）

作成: 2026-09-29 / 対象: iekanko.jp（くらしの制度ナビ）

## 0. 背景（なぜこの設計か）

GSC調査の結論: 8/20の表示回数急落は**技術障害でもインデックス除外でもなく、
Googleアルゴリズムによる「サイト全体の品質/スパム降格」**。
- URL検査: 登録済み・9/28クロール成功・取得成功・正規化正常・手動対策なし。
  → 技術は健全なのに順位だけ消えた ＝ アルゴリズム降格で確定。
- 降格の主因: **① 中古ドメイン評判（旧アフィリエイト）＋ ② 大量・薄い自動生成ページ**。

本書は主因②への対策（コンテンツ側の設計）。①はドメイン移行で別途対応。

## 1. 現状のページ構成（実測 2026-09-29）

| 種別 | 枚数 | 性質 |
|---|---:|---|
| 個別制度 `area/*/seido/*` | **3130** | 各ページの固有情報は dt/dd 4項目＋短FAQのみ。テンプレ率が高い |
| 比較ハブ `hikaku/` | 44 | **既存の武器**。カテゴリ別に62自治体を横断比較 |

| ライフイベント `area/*/{event}/` | 62 | 自治体×ライフイベント |
| 自治体トップ `area/tokyo/*/` | 62 | 自治体の入口 |
| 暮らしデータ `kurashi-data/` | 7 | 統計 |
| **総計** | **3616** | うち index 対象 約3581 / noindex 35 |

### 個別制度3130枚の内訳（重複度）
- ユニーク題名: 2127
- **同名が10自治体以上に存在 = 795制度**（児童手当×58、妊婦健診×59、国民年金免除×48、
  帯状疱疹×44、マル障×44、産後ケア×44…）→ **ほぼ同一の複製ページ**。重複・薄いの直撃。
- **1自治体のみの固有題名 = 1974制度** → 本来の差別化資産だが、1枚ずつは薄い。

## 2. 基本戦略：「集約ファースト／少数精鋭」への転換

> 検索結果に出す（index）ページを絞り込み、評価とクロール予算を
> **比較ハブ・自治体ガイド・固有性の高い制度** に集中させる。
> 個別制度データは消さず `noindex,follow` で残す（ユーザーは閲覧可・内部リンクは生きる）。

**Phase 1 実装結果（2026-09-29, 方針C = STD≥5＋金額fact必須）**:
- 個別制度ページ: index **3096 → 1729** / noindex 1401
  （内訳: 標準/複製 909・金額なし 455・薄い 3・低信頼 34）
- サイトマップ URL: 約3,581 → **2,215**（複製と金額なしの薄いページを除外、固有×金額ありを保持）
- `build/verify.sh` はラウンドトリップ冪等性 PASS（programs=3130 / facts=14857 不変＝facts欠落なし）
- 当初案の「600〜900」は、固有制度2,187のうち1,489が具体的金額を持ち差別化資産であるため
  非現実的と判明。実測に基づき **半減（約2,215）を Phase 1 の着地点**とした。
  さらに絞る場合は環境変数で調整可（`SEIDO_STD_MUNIS=3` 等、下記6章）。

Googleへのメッセージを「薄い複製が3000枚」から
「一次情報を横断比較した唯一無二のハブが数百枚」へ変える。

### インデックス方針（3層モデル）

| 層 | 対象 | robots | 役割 |
|---|---|---|---|
| **A. ハブ（主戦力）** | hikaku / ranking / guide / tokushu / kurashi-data | index | 検索意図に応える独自比較 |
| **B. 自治体・イベント入口** | 自治体トップ62 / ライフイベント62 | index | 地域名検索の受け皿 |
| **C. 個別制度** | seido 3130 | 原則 **noindex,follow**。ただし後述の「固有性ゲート」を通った厳選のみ index | 詳細・出典の参照先 |

## 3. C層「固有性ゲート」— どの個別制度を index に残すか（実装済み）

`build_program()` の index 判定を、現行の confidence ゲートに **固有性条件** を AND で追加した。
環境変数で全条件を調整可能（`SEIDO_UNIQ_GATE` / `SEIDO_STD_MUNIS` / `SEIDO_MIN_FACTS` /
`SEIDO_REQUIRE_AMOUNT`）。gate 判定は robots メタと**サイトマップ登録の両方**を同時に制御する。

```
index = (現行ゲート: 平均confidence≥82 かつ reliability_status≠needs_review)
        AND is_indexworthy(program)

def is_indexworthy(p):
    # ① 標準/複製制度は除外（ハブに集約するため）
    if 同名 normalized_title の自治体数 >= 5:      return False   # 795制度＋αを noindex
    # ② 自治体固有の金額・内容があるか
    if not has_local_amount(p):                    return False   # amount_text が空/一律なら除外
    # ③ 固有情報の最低量（薄すぎるページを除外）
    if 固有dt/dd数 < 3:                            return False
    return True
```

- 想定結果: 個別制度の index 対象は **数百枚**（1974の固有制度のうち、金額と情報量が揃うもの）。
- 795の標準制度ページは全て noindex → 対応する hikaku ハブが検索の受け皿。
- 閾値（5自治体・3項目など）は `verify.sh` の期待値更新とセットで調整。

## 4. A層 ハブの独自価値強化（回復の本丸）

noindex で薄いページを引いた後、**残す数百枚に“人の編集価値”を足す**のが回復の決め手。

### 4-1. 比較ハブ hikaku（44枚）に「自動生成でない洞察」を付与
各ハブ冒頭に、データから導いた**独自の要約コメント**を生成（テンプレ文でなく数値駆動）:
- 例（児童手当比較）:「62自治体中、区独自の上乗せがあるのは◯自治体。最も手厚いのは
  △△区（所得制限なし＋◯円上乗せ）。一方、申請が電子化済みは◯自治体のみ…」
- 「選び方の注意点」「よくある誤解」「手続きのコツ」を1次情報ベースで1〜3段落。
- 出典・最終確認日を明示（既存の confidence/出典整備を前面に）。

### 4-2. 自治体トップ62枚を「その自治体の制度まるわかりガイド」に格上げ
- 使える制度一覧（カテゴリ別）＋ その自治体の**特徴コメント**（独自制度の有無・手厚い分野）。
- 近隣自治体との差分（「隣の◯区にあって当区に無い制度」）＝ 唯一無二の比較価値。

### 4-3. 検索意図の取りこぼしを埋める新規ハブ（優先度順）
既存44カテゴリで未カバーの高需要テーマを追加（キーワードは GSC「クエリ」で確定してから）。
- 「◯◯（制度名）＋ 東京 比較」「◯◯ もらえる 自治体」系の一次比較記事。

## 5. 内部リンク・サイトマップの再設計

- **サイトマップは index 対象のみ**に限定（現状は seido も全部載っている）。noindex ページを除外し
  クロール予算をハブへ集中。`build_site.py` のサイトマップ生成を index フラグで絞る。
- 個別制度（C層）→ 該当ハブ（A層）への「比較で見る」導線を必ず設置（follow は残すので評価は流れる）。
- ハブ同士・ハブ↔自治体トップの関連リンクを強化（トピッククラスタ化）。

## 6. 実装ステップ（build_site.py / DB 中心・docs直編集はしない）

1. **固有性メタの用意**: `normalized_title` ごとの出現自治体数を集計し、
   `has_local_amount` / 固有dt/dd数 を算出するヘルパを `build_site.py` に追加。
2. **gate 拡張**: `build_program()` の robots 判定に `is_indexworthy()` を統合。
3. **サイトマップ絞り込み**: index ページのみ出力。
4. **ハブ強化**: hikaku/自治体トップに数値駆動の独自コメント生成関数を追加。
5. **再生成→検証**: `PYTHONHASHSEED=0 python3 build/build_site.py` →
   `EXP_FACTS=... EXP_PROGRAMS=... bash build/verify.sh`（期待値を新方針で更新）。
6. **段階デプロイ**: まず Phase1（noindex整理＋サイトマップ絞り）を1回で反映し、
   GSC「ページ」レポートで index 数の推移とクロール挙動を観察。次に Phase2（ハブ強化）。

## 7. 期待できる効果と注意

- **効果**: 薄い複製の一掃で scaled-content 判定のトリガーを外し、
  評価とクロール予算が数百の高品質ハブへ集中 → 中長期でハブが順位回復しやすくなる。
- **注意①**: アルゴリズム降格の回復は**数週間〜数ヶ月**。即効性はない。
- **注意②**: 中古ドメインの評判（主因①）が重い場合、コンテンツ改善だけでは頭打ちの可能性 →
  並行して**新ドメイン移行**の検討を推奨（本設計の資産はそのまま移せる）。
- **注意③**: noindex 化は「検索から消す」だけでユーザー閲覧・内部リンクは維持。PVの内部導線は保つ。

## 8. 最初の一歩（提案）

Phase1 = 「固有性ゲート＋サイトマップ絞り込み」を build_site.py に実装し、
index 枚数を実測（何枚に絞れるか）→ verify 通過 → まとめて1回デプロイ。
その後 GSC で index 数の推移を見ながら Phase2（ハブ強化）へ。
